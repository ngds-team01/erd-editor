  - `meta.json`의 "커밋 안 한 변경 있음"은 실행기(`loadtest/src/exp2*.ts`)와 아래 봇 수정만 커밋 전이었다는 뜻

## (a) 접속 중 강제 종료 → 재동기화 시간

편집 중 이 문서의 연결이 가장 많은 편집 서버 파드를 30초마다 `kubectl delete pod --force --grace-period=0`.

| 반복 | 삭제 | 끊긴 연결 | 재동기화 p50 / p95 / 최대 (ms) | 못 붙은 봇 | 수렴 |
| --- | --- | --- | --- | --- | --- |
| 1 | 10 | 151 | 547 / 631 / 657 | 0 | PASS |
| 2 | 10 | 158 | 590 / 828 / 866 | 0 | PASS |
| 3 | 10 | 158 | 583 / 952 / 1125 | 0 | PASS |
| 전체 | 30 | 467 | 572 / 832 / 1125 | 0 | 3/3 |

- 재동기화 시간은 봇이 끊김을 알아챈 때부터 다시 동기화될 때까지
- kind에서는 강제 종료 뒤 컨테이너가 실제로 죽어 연결이 끊기기까지 약 2초가 걸림 (`kills.csv`의 `detect_ms` p50 2089ms · p95 2263ms)
- 지운 때부터 마지막 봇이 다시 동기화되기까지 (`recovered_ms`): p50 2700ms · p95 2966ms · 최대 3205ms. 이렇게 재도 5초 안
- close code는 모두 1006, 실패한 재접속 0회 (남은 파드에 첫 시도로 붙음)
- 수렴 PASS = 끊긴 동안 한 편집까지 모든 봇과 새 관찰자 문서가 같음

## (b) 전원 이탈 후 강제 종료 → 유실 수

60초 편집 → 봇 전원 이탈 → 모든 파드에서 문서가 내려간 뒤 편집 서버 파드를 **모두** 강제 종료 → 새 파드에 관찰자가 붙어 서버 데이터만으로 복원한 문서를, 봇이 나가기 전 상태와 비교.

| 경우 | 실행 | PASS | 빠진 추가 / 삭제 | 서버 복원 p50 / p95 / 최대 (ms) | 관찰자 동기화 p50 / p95 / 최대 (ms) | 복원 출처 |
| --- | --- | --- | --- | --- | --- | --- |
| 스냅샷 전 | 30 | 30/30 | 0 / 0 | 105 / 165 / 215 | 139 / 223 / 274 | Streams만 30 |
| 스냅샷 후 | 30 | 30/30 | 0 / 0 | 59 / 120 / 151 | 107 / 235 / 328 | 스냅샷 30 |

- 스냅샷 전: 워커를 0개로 줄인 채 실행 (Streams 기록만으로 복원)
- 스냅샷 후: 봇이 나가고 40초(워커 주기 30초 + 여유) 뒤 삭제. 30번 모두 서버 로그가 "스냅샷 있음, 기록 0항목" (스냅샷만으로 복원)
- 서버 복원 = 새 파드 로그의 `복원 완료 …초`, 관찰자 동기화 = 관찰자 접속부터 동기화까지 (서버 복원 포함)
- 반복별 값은 각 폴더의 `report.md`
